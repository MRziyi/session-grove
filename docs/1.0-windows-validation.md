Validated on Windows with Node.js 24.21.0, Git 2.53.0.windows.2, Edge, Codex 0.155.0-alpha.16.3 and the pinned Claude Agent SDK 0.3.283. All public screenshots use synthetic sessions. Private transcripts, keys, local profiles and raw benchmark reports are excluded from Git.

## Resource measurements

The Git workload uses 40 synthetic sessions, 20 turns per session and an isolated local bare repository. These are local CPU/storage measurements, not internet transfer throughput. Timing varies with disk, antivirus, cache state and profiling overhead.

| Hotspot | Evidence | Change / result |
| --- | --- | --- |
| SQLite write amplification | Creating 400 sessions took 38,598 ms with separate record/revision/entity commits. | Group new revisions, branches, forks and ingests into transactions, reusing an existing transaction when present. Same workload: 1,936 ms, about 20× faster. An injected write failure verifies complete rollback. |
| Main-thread import latency | New-device Pull reached about 593 ms maximum event-loop delay in the initial Git audit. | Yield between directory batches and record batches; stream records and avoid reading every graph twice. Subsequent runs: 89–95 ms. Total import time remained around 2.3–2.5 seconds. |
| Memory while decoding records | Whole-file parsing keeps the JSONL buffer and split lines live. | Stream record files. A separate-process 32 MiB fixture peaked at 99 MiB RSS for whole-file decoding and 93 MiB for streaming. Decoding took 51 vs 97 ms: bounded memory and responsiveness trade some decoder throughput. |
| Redundant network work | An unchanged Pull previously checked the remote and fetched again. | One remote-reference check, no fetch, no session-index reread. Successful Push updates the local tracking ref, so the next unchanged operation also avoids fetch. |
| Disposable-cache flushes | CPU profiling attributed roughly 0.5 seconds to forced flushes of reconstructable Git cache files. | Keep atomic replacement while omitting per-file `fsync` for this cache only. SQLite and credential/config writes retain durability. Initial synthetic Push improved from roughly 3.0–3.2 s to 2.6 s. |
| Native discovery | Repeated instance/catalog linear searches scale quadratically. | Index file/native identities for each scan. Reuse immutable parsing for forks, avoid repeated base-history reads on ingest and duplicate Claude transcript reads on import. |
| Idle CPU / requests / database work | 200 repeated status/list cycles took about 20–33 ms. | Zero Git commands, zero remote calls and zero SQLite row changes. Metadata-only Push changed no transcript record files. |
| Model-request latency | Synthetic live classification/naming requests completed in about 2.6–2.7 s each. | Default concurrency is two, configurable to 1–4, with one shared minimum start interval. Failures pause new starts until Retry; removing the key cancels all active requests. |

The representative final Git run used approximately 143–144 MiB RSS at the later phases. Warm capture was about 15 ms; unchanged Pull was about 344 ms. These are samples, not performance guarantees. A single very large native record and initial parsing of large histories can still block; the existing record-size limits and bounded parse caches remain relevant.

Electrical energy was not measured. CPU time, disk flushes, allocation pressure, request counts and idle behavior are the available energy proxies; no watt-hour or battery-life improvement is claimed.

## Naming prompt review

An operator-selected 42-branch project provided 18 named fork points. Five selected nodes were compared with a more specific candidate instruction. It improved some generic or opening-word-heavy labels, while other names were equivalent or less natural. This small qualitative sample did not justify a blanket prompt replacement. Existing names and the production prompt were preserved. Detailed evidence and candidate names remain in the private local report, outside the public repository.

## Context configuration boundaries

Codex exposes `model_context_window` and `model_auto_compact_token_limit`; the configured compaction scope is preserved. Profile-specific overrides take precedence. See the [official Codex configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference).

Claude exposes `CLAUDE_CODE_AUTO_COMPACT_WINDOW` as an auto-compaction budget from 100,000 to 1,000,000 tokens, capped by the model’s actual window. Grove writes it in the user settings environment map and preserves any existing percentage override. See [Claude environment variables](https://code.claude.com/docs/en/env-vars). Project settings, environment variables and per-launch overrides can take precedence over user configuration. Empty fields remove the edited override; changes are intended for newly opened client sessions.
