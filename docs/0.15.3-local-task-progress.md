# 0.15.3: observable Trash operations

Move to Trash now requires all selected paths to be inactive. For a selected tree, both UI and server check every live branch, including branches belonging to another tool. The list offers Deactivate with the active count first; after deactivation, Trash becomes available. An active endpoint shows Deactivate and does not expose Trash. Trash no longer silently attempts deactivation and then discards the path even if deactivation failed.

Trash and Move to Recovery publish local-task events and retain operation status for polling. Their bounded progress indicator names the actual phase: preparing paths, copying records (with record counts), saving/compressing the backup, updating Trash, verifying recovery, removing client files, and cleaning unused records. A phase without a measurable total uses indeterminate progress. Per-copy failures remain explicit.

Recovery preparation yields between record batches and compresses through asynchronous zlib. It pins record storage while preparing the snapshot. Local mutation requests cannot race an in-progress Trash operation; read requests and progress events remain available between batches. Recovery moves perform library cleanup once after the batch rather than once per copy.

The old cleanup performed a full SQLite VACUUM after every removal. Routine Trash now deletes unreferenced records and uses a passive WAL checkpoint, allowing SQLite to reuse free pages without rewriting the entire database for each action. Physical file compaction is not part of ordinary Trash completion.

The divider grip is an in-flow child of the real separator column rather than an absolutely positioned pseudo-element centered on the whole editor. It follows mouse dragging and keyboard resizing; the ribbon overlay keeps its editor-wide coordinate system.
